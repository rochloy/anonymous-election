## 1. Goal

Lift the council's real-PII **NO-GO** by breaking the identity↔vote linkage (findings **F2/F3/F3b**), while folding in the orthogonal hygiene items (**Option B**) and the deferred `data/members.csv` git-history purge (**F1**).

Architecture target: **Option A — split-service / minimized-linkage.** No plaintext identity↔vote register survives, in any table or durable log, for either channel. This clears the **real-PII / GDPR NO-GO** — the blocker that actually prevents going live with real data (real gmails in git history + intact identity↔choice registers).

**Scope boundary (path A, user-approved 2026-09-17):** Option A does **not** deliver information-theoretic anonymity against a `SUPABASE_SERVICE_ROLE_KEY` / DB-superuser adversary. The security red-team proved (C3) that physical insert order (`xmin`/`ctid`) plus millisecond `tokens.used_at` forms a *total order* that zips member→ballot 1:1 for ~300 voters, and column-level coarsening cannot touch physical row order. Defeating that adversary requires the deferred crypto wave (blind signatures + shuffle — §11). v0.13.0 therefore **re-scopes §3 to be honest about which adversaries it defeats** (§3) and documents the service-role timing residual as explicitly out-of-scope (§10), rather than overclaiming a guarantee the design cannot honor.

## 3. Threat model (authoritative, re-scoped per path A)

The DRAFT of this section named the `SUPABASE_SERVICE_ROLE_KEY` holder as in-scope and promised to defeat "a timing side-channel." The security red-team unanimously found (C1/C2/C3) that Option A **cannot** honor that promise against that adversary. Rather than ship an overclaiming guarantee, §3 is re-scoped to state honestly which adversaries v0.13.0 defeats and which are deferred.

- **In-scope adversaries (v0.13.0 MUST defeat):**
  - **The PUBLIC** — via PostgREST/RLS. `ballots` exposes `ballot_id → candidate_id` only after close and carries no `member_id`; `paper_ballots` / `vote_audit_log` have no public access (`schema.sql:147-152`). No public path links a person to a vote.
  - **OTHER VOTERS** — no authenticated non-admin surface reveals another member's choice.
  - **A compromised admin *session*** (stolen `ADMIN_SECRET`, no DB key) — reaches only what the RPCs + role gate (§7) expose: participation (member + channel + coarse time), never the choice, never a join handle.
- **Deferred adversary (explicitly OUT of scope — §10, §11):** a holder of `SUPABASE_SERVICE_ROLE_KEY` or direct DB/superuser access. Against this adversary, insert-order/`xmin`/`ctid` + ms `tokens.used_at` correlation (C3) is a total order that schema shape cannot close. This is the crypto wave's charter, not v0.13.0's.
- **The one hard guarantee (v0.13.0, in-scope adversaries):** no anonymous-domain row (`ballots`) may be linkable to the member who cast it — through a **column, a shared identifier, or a durable log row** — after the vote is recorded. (Timing side-channels against the service-role adversary are the deferred residual, not covered by this guarantee.)
- **Register-destruction requirement (drives §5, from C1/C2):** it is not enough to *hide* the identity↔choice register from in-scope adversaries — the durable register must be **destroyed at the source**. `vote_audit_log` currently *is* an intact register (`member_id + ballot_id + candidate_id`, `migration_option_e_paper_ballots_part2.sql:164-166`, `:252-254`); a self-join on `ballot_id` reconstructs 100% of paper votes. The shared `ballot_id` (paper_ballots PK == `ballots.ballot_id`) is a one-hop join. Both must be eliminated, not merely access-gated.
- **Key correction from oracle (drives §5):** timestamp coarsening alone is insufficient. **Stable join handles** (`ballot_id`, `short_code`, `receipt_code`, `batch_id`, sequence/insert order) re-link identity→ballot→candidate even with coarse time. The severance must eliminate the handles, not just the clock.

## 4. Pillar B — Digital two-phase voting

**Current (coupled):** the voter UI posts `{rawToken, candidateId}` together (`app/vote/[token]/page.tsx:54-60`); the API forwards `p_token_hash + p_candidate_id` into one RPC (`app/api/vote/route.ts:30-53`); `submit_anonymous_vote` inserts the ballot and marks the token used in one transaction (`migration_option_e_paper_ballots_part2.sql:364-437`). This is F3/F3b.

**Target (split at the boundary):**
1. **Redeem** — server validates the token and **atomically reserves the entitlement** (`SELECT … FOR UPDATE` on the single voting token; abort on zero rows), returning an **anonymous voting credential**. This step sees the member/token but **never a candidate**.
2. **Cast** — voter presents the credential + candidate. This step sees the credential + candidate but **never the member/token**. Inserts into anonymous `ballots` only.
- The two steps share no member-derived identifier. The credential must be unlinkable to the token/member (opaque, single-use, server-verified).
- **Reserve, don't consume (H2 — ops red-team):** Redeem must **not** mark the token terminally used (`is_used=TRUE`, `migration_option_e_paper_ballots_part2.sql:435`). If it did and Cast then failed, the token would be burned with no ballot and an unlinkable credential — an unrecoverable dead state for on-call, and any rollback to single-phase would strand mid-flight voters. Instead Redeem writes into a **voting-credential reservation table** (credential hash, reserved-at, expiry); Cast atomically converts the reservation → `ballots` insert and finalizes token consumption; an unconverted reservation expires and **releases the entitlement** (mirrors the paper reserve/spoil model, §6). The legacy single-phase `submit_anonymous_vote` stays deployed but **dormant behind a feature flag** for safe rollback until two-phase is proven.
- Ballot payload must remain fully **opaque random** (no `member_id`/`candidate_id`/timestamp embedded) — re-affirm the v0.3.0 opaque-ballot-id invariant, enforced by the pgTAP body assertion that replaces the F15 version-floor (§8).
- **Accepted residual (C3):** two-phase adds a *second* correlatable timestamp per voter (reserve + cast). Against the deferred service-role adversary this is strictly worse than single-phase, but that adversary is out of scope for v0.13.0 (§3, §10); against in-scope adversaries the reservation table is behind the RPC boundary and carries no member handle.

## 5. Pillar C — Paper severance (join-handle elimination)

Paper voting is already physically two-phase; **the admin workflow does not change.** The defect is that recording writes identity and choice into joinable durable state.

**Current leaks (source-verified):**
- `paper_ballots` row co-locates `member_id` (`schema.sql:99`) with `candidate_id` (`schema.sql:103`) after `submit_paper_vote` (`migration_option_e_paper_ballots_part2.sql:243-245`).
- Even dropping `candidate_id`, `paper_ballots` still holds `member_id + ballot_id`, and `ballots` maps that same `ballot_id → candidate_id` (`schema.sql:97-103`; `schema.sql:79-83`) — the register survives via the **`ballot_id` join**.
- `vote_audit_log` co-stores `member_id + ballot_id (+ candidate_id)` on issue and vote (`migration_option_e_paper_ballots_part2.sql:164-168`, `:252-254`).
- Preprinted ballot IDs embed `batch/index/epoch` in a plaintext HMAC payload (`migration_option_e_paper_ballots_part2.sql:57-68`; `hmac_sign` returns `payload || '.' || sig`, `schema.sql:161-178`).
- `short_code` is displayed under the member in the dashboard (`app/admin/dashboard/page.tsx:2462-2470`) and returned by member search (`app/api/admin/members/route.ts:66-120`).

**Target rules:**
1. On successful paper cast, the identity plane must **not retain `member_id + ballot_id` together** — null/redact `member_id` on `paper_ballots` (or move issuance to an unlinkable participation record). `candidate_id` is **removed from `paper_ballots` entirely**.
2. **Destroy the durable register, don't hide it (C1 — security red-team):** `vote_audit_log` currently stores `member_id + ballot_id (+ candidate_id)` on issue and vote (`migration_option_e_paper_ballots_part2.sql:164-166`, `:252-254`) — a self-join on `ballot_id` reconstructs every paper vote, and the register persists in backups regardless of access controls. The audit log must **stop recording `ballot_id` and `candidate_id` alongside `member_id`**: split into (a) an identity/participation audit (member + channel + coarse time, no ballot/choice handle) and (b) a ballot/choice audit that carries no member-linkable key. Retro-scrub any existing rows on migration.
3. **Eliminate the shared `ballot_id` join (C2 — security red-team):** `paper_ballots.ballot_id` PK equals `ballots.ballot_id` (`schema.sql:98`; `migration_option_e_paper_ballots_part2.sql:229-230`), so any surviving `member_id ↔ ballot_id` artifact re-links to `candidate_id` in one hop. Either (a) the paper cast must not persist the anonymous `ballot_id` in any member-reachable row, or (b) the anonymous `ballots` row must use an independent identifier with no stored mapping back to `paper_ballots`. The severance of member_id (rule 1) and the register destruction (rule 2) are only sufficient if this shared handle is also broken.
4. **Audit separation:** the ballot/choice audit and the identity/participation audit must not share `ballot_id`, `short_code`, `receipt_code`, `batch_id`, or exact timestamp.
5. **Opaque paper IDs:** preprinted ballot payloads become pure-random (no batch/index/time).
6. **Prune member-linked surfaces:** participation/dispute views and durable logs must not pair `short_code`/`ballot_id`/`batch_id`/`receipt_code` with member identity; existing admin surfaces (dashboard member card, member-search API) pruned accordingly.
7. **Correction = ballot-keyed:** scan the physical ballot → edit `ballots.candidate_id WHERE ballot_id`. Never a member lookup. Authorization is possession of the paper.

## 6. Pillar D — Dedup: hard cast-time mutual exclusion

- The voting **token** is the single entitlement. Both digital-redeem (§4.1) and paper-issue **must `SELECT … FOR UPDATE` the token first**, require exactly one active entitlement, atomically mark it consumed, and **abort if zero rows updated**.
  - Fixes the current race: paper issue checks the token without locking and ignores a zero-row update while still returning success (`migration_option_e_paper_ballots_part2.sql:121-168`).
- **Delete** the "paper wins; tally deduplicates" branch (`migration_option_e_paper_ballots_part2.sql:216-223`). A blind tally cannot do member-aware dedup.
- **Tally** = blind count of anonymous `ballots`. No member-level reconciliation.
- **Spoil/void releases the reservation** — but **only for unrecorded PAPER reservations, before any anonymous-ballot insert**, and must never touch a digital/email token's usage (cf. `migration_wave3_paper_token_reserve.sql:139-150`, `migration_fix_spoil_frees_token.sql:45-55`). Correction after cast must never release entitlement.

## 7. Decision E — Participation / dispute view + admin role separation (R, built now)

**Deployment reality:** multi-admin at launch with separated duties → full role separation (R) is a genuine control, built in this wave (not deferred).

**Purpose (lawful basis):** dispute resolution — "did this member already vote?". Legitimate interest, narrow, mapped to a dedicated role.

**Admin role separation (R):**
- Introduce an `admin_roles` model (table/column) with at minimum a **`dispute-resolution`** role distinct from **general admin**. `requireAdmin()` currently enforces no role — all admins pass (`app/api/admin/auth.ts:46-99`); replace the bare check at anonymity-sensitive routes with `requirePermission(<permission>)`.
- Scope RBAC **surgically** to the anonymity-relevant surfaces (participation/dispute view; ballot-keyed correction; PII purge) — not a blanket rewrite of every admin action. The full permission matrix is enumerated in `writing-plans`.
- **Security-sensitive:** the permission gate must be tested against **known-bad input** (a wrong-role/no-role request must be *proven* to be refused, per AGENTS.md guard-testing discipline), not only a happy-path pass.

**Participation view (behind `dispute-resolution` role):** surfaces existing identity-domain data (`tokens.is_used/used_at/channel_sent`): `member + channel (DIGITAL/PAPER) + coarse timestamp`. Data-minimization guardrails are mandatory:
- **Content firewall:** never join to / display `candidate_id`.
- **No handles:** no `ballot_id`, `short_code`, `batch_id`, `receipt_code`, or correction handle.
- **Coarse time both sides:** date (or hour max); anonymous `ballots.cast_date` stays DATE-precision (`schema.sql:85`).
- **Access log:** record viewer (`admin_sessions.id`), role, action, row count — not exported member lists.

## 8. Option B — hygiene items (folded, written C-forward)

- **F15 (revised per H1 — ops red-team):** the DRAFT version-floor sentinel is **theatre** — it asserts a version *tag* but never inspects the function *body*, so a higher-version leaky `CREATE OR REPLACE` passes (there is already a leaky sibling at `migration_option_e_paper_ballots_part2.sql:416`), and a manual SQL-Editor apply bypasses it entirely. Replace it with a **pgTAP body/output assertion on the live catalog**: `pg_get_functiondef` of each ballot writer must **not** match the leaky payload pattern, and the last-inserted `ballot_id` must match the opaque regex `^(PAPER|DIGITAL):[0-9a-f]{64}\.[0-9a-f]{64}$`. Per AGENTS.md guard-testing discipline, **prove the assertion RED first** (run it against a known-leaky writer and confirm it fails) before trusting a green run.
- **F11:** redact name/email/magic-link from dry-run token-dispatch logs (`app/api/admin/tokens-dispatch/route.ts:167-170`).
- **F14:** tighten prod CSP — remove `unsafe-inline`/`unsafe-eval` where feasible (`next.config.ts:7-18`); keep camera `Permissions-Policy` correct for `html5-qrcode` (`next.config.ts:33-35`).
- **F4:** introduce role-specific Supabase clients vs the service-role singleton backing public routes (`lib/supabase-server.ts`).
- **Rate limiter:** reusable IP/bucket pre-handler using only IP/bucket — never token/candidate (`proxy.ts`).

## 10. Documented residual (post-Option-A) — accepted, deferred to crypto wave

- **Service-role timing/insert-order correlation (C3 — security red-team, ACCEPTED residual).** Against a `SUPABASE_SERVICE_ROLE_KEY` / DB-superuser adversary, physical insert order (`xmin`/`ctid`) plus millisecond `tokens.used_at` (written in the cast transaction, `migration_option_e_paper_ballots_part2.sql:435`) forms a **total order** that zips member→ballot 1:1 for the ~300-voter population. Column/timestamp coarsening (DATE-precision `ballots.cast_date`, `schema.sql:85`) does **not** touch physical row order, so this is not a "weak" surface — it is a full reconstruction path for that adversary. Two-phase digital (§4) adds a second correlatable timestamp, making it marginally worse. **This is out of scope for v0.13.0 by decision (path A, §3):** closing it requires the deferred crypto wave (blind signatures + insert shuffle / heap rewrite at close — §11). Record in DPIA/RoPA as a known, accepted residual with the service-role adversary named, and constrain who holds `SUPABASE_SERVICE_ROLE_KEY` as a compensating operational control.
- **Handle-based operator correlation** is *closed* within v0.13.0 by §5 (register destruction, shared-`ballot_id` elimination, handle stripping) — only the timing/insert-order vector above remains for the deferred adversary.

## 11. Non-goals (explicitly out of scope for v0.13.0)

- Full cryptographic anonymity (blind signatures, mixnet/shuffle) — deferred to a dedicated follow-up wave with a `@council` red-team. Option A's split-service design is a natural substrate for it (additive, not a rewrite).
- Blanket admin RBAC across *all* admin actions — v0.13.0 scopes role separation surgically to anonymity-sensitive surfaces (§7); a broader permission matrix is out of scope.

## 12. UX impact summary

- **Voter — digital:** visible. Two-phase flow (redeem → cast) + bulletin-board receipt/verify semantics; possible "tally pending" state.
- **Voter — paper:** none. Scan-issue / scan-record / scan-correct unchanged.
- **Admin — dashboard member card:** loses paper-ballot handles (`short_code`/ballot linkage). Designer-owned surface (`app/admin/dashboard/page.tsx`) → **@designer pass** required.
- **Admin — role separation (R):** new `dispute-resolution` role vs general admin; role-assignment surface + role-gated navigation. Anonymity-sensitive routes move behind `requirePermission`.
- **Admin — new participation/dispute view:** behind the `dispute-resolution` role, content-firewalled, access-logged.
- **Admin — bulletin-board verify:** `app/verify/page.tsx` semantics shift from identity lookup to inclusion verification.

## 13. Top risks to carry into `writing-plans` (oracle- + red-team-ranked)

1. **Durable register survives severance (C1)** — destroy the `vote_audit_log` identity↔choice register at the source (split identity vs ballot/choice audit, retro-scrub existing rows); access-gating is not enough (§5.2).
2. **Shared `ballot_id` re-links in one hop (C2)** — break the `paper_ballots.ballot_id == ballots.ballot_id` join, not just null `member_id` (§5.3).
3. **Stable-identifier relinkage beats timestamp coarsening** — kill `member_id + ballot_id` co-location in tables *and* logs (§5).
4. **Two-phase burned-entitlement dead state (H2)** — Redeem reserves (does not consume); Cast converts; unconverted reservation expires and releases; legacy single-phase kept dormant behind a flag for rollback (§4).
5. **Guard is theatre unless proven RED (H1)** — the F15 replacement pgTAP body assertion must be shown to fail against a known-leaky writer before it is trusted (§8).
6. **Race at entitlement consumption** — both channels lock/consume the same token first; abort on zero rows (§6).
7. **Operational side-channels** — opaque paper IDs; strip `short_code`/`batch_id`/`receipt_code` from any member-linked surface or durable log (§5).
