# Design

## Context

Current state (from `supabase/migration_option_e_paper_ballots_part1.sql`): five actor columns exist, all FK'd to `members(id)`, all NULL, and unwritable by RPCs since `migration_paper_assign_phase_gate.sql` removed the `issued_by` write. The fixed-in-place precedent is `migration_fix_admin_id_fk.sql` (v0.4.4): `vote_audit_log.admin_id` and `nomination_adjudications.admin_id` were repointed to `admin_sessions(id) ON DELETE RESTRICT`. Wave 6 (`migration_wave6_paper_severance.sql`) uses the same target for the blank-plane actor columns. See proposal.md — Why.

Constraints: Postgres constraint names for the existing FKs were autogenerated (e.g. `paper_ballots_issued_by_fkey`) — the migration must not hard-assume them; and the change applies via Supabase MCP / SQL Editor as item 39 of the canonical run order, per the project's final-writer migration discipline.

## Goals / Non-Goals

**Goals:**
- Repoint the five FKs to `admin_sessions(id) ON DELETE RESTRICT` in one atomic, idempotent-where-practical migration.
- Provable data-safety: pre-check that all five columns are entirely NULL before altering constraints (fail loudly otherwise).
- Keep canonical run order and CHANGELOG coherent.

**Non-Goals:**
- Re-enabling RPC writes to actor columns (separate decision, needs attribution UX review).
- `admin_principals`, advisory-lock fix, audit-fallback hard-fail (separate backlog items).
- Any application-code change.

## Decisions

1. **`ON DELETE RESTRICT` (not SET NULL / CASCADE).** Matches both precedents (`migration_fix_admin_id_fk.sql`, Wave 6). Attribution, once written, must not silently vanish with a purged session. Alternative considered (SET NULL) preserves purge convenience but loses attribution history — wrong default for an audit-adjacent column.
2. **Dynamic constraint discovery.** Drop FKs by looking up actual constraint names from `information_schema.table_constraints` (join `key_column_usage`) rather than assuming `*_fkey` names — idempotent and robust to naming drift. Alternative (hard-coded names) is brittle.
3. **Guarded NULL check as a hard precondition.** `DO` block asserts `NOT EXISTS (SELECT 1 ... WHERE <col> IS NOT NULL)` for each of the five columns and raises before touching constraints. If a future state has data, the migration stops instead of silently changing semantics mid-election.
4. **No `ON DELETE` clause currently exists on these FKs → repoint resets semantics to RESTRICT.** Explicitly chosen semantics change, documented in the spec (session-purge scenario).
5. **Final-writer discipline.** The new migration is the only definition of these constraints going forward; it is appended to the canonical run order in `docs/TECHNICAL_GUIDE.md` as item 39, running after item 38. (`seed.sql` stays last of the *base rebuild* — item 21 — but later migrations run after it; that is the established convention.)

## Risks / Trade-offs

- [RESTRICT blocks purge of an attributed `admin_sessions` row] → Acceptable: actor columns unwritten for now; when writes are re-enabled, attribution retention wins over session cleanup convenience. Session purge housekeeping must tolerate FK-blocked skips.
- [Live DB may already hold unexpected rows in these columns] → NULL pre-check raises; rerun safe after investigation.
- [Constraint-name drift across environments] → dynamic discovery via information_schema.
- [Mid-election application] → NOT to be applied mid-election. Apply only in SETUP phase alongside other maintenance. Recorded as a task gate.

## Migration Plan

1. Apply `supabase/migration_repoint_paper_actor_fks.sql` via Supabase MCP / SQL Editor (canonical item 39, after the wipe RPC; SETUP phase only).
2. Verify: `information_schema` shows all five FKs → `admin_sessions(id) DELETE RESTRICT`; known-bad input test: attempt to set `issued_by` to a member UUID → must FK-violate; set to a real session UUID → succeeds (then revert).
3. Rollback: re-point to `members(id)` via a reverse migration (written but not run; columns are NULL so both directions are trivial alter-constraint).
