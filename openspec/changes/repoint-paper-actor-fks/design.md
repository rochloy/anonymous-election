# Design

## Context

**Live-DB verified 2026-09-30 (SETUP phase):** the original "five wrong FKs" premise was stale — it was read from pre-Wave-6 historical migrations. Ground truth: Wave 6's paper severance already rebuilt `paper_ballots` with correct actor FKs (`checked_in_by` / `spoiled_by` / `voided_by` → `admin_sessions(id) ON DELETE RESTRICT`, confirmed live via `pg_constraint`), and the pre-Wave-6 `issued_by` / `recorded_by` columns no longer exist. **Exactly one wrong actor FK remains: `paper_ballot_batches.generated_by` → `members(id)` (NO ACTION)**, created by `migration_option_e_paper_ballots_part1.sql` and never touched by later waves. The column is all-NULL (3 batch rows). The fixed-in-place precedent is `migration_fix_admin_id_fk.sql` (v0.4.4): `vote_audit_log.admin_id` repointed to `admin_sessions(id) ON DELETE RESTRICT`. See proposal.md — Why.

Constraints: the existing constraint name is the autogenerated `paper_ballot_batches_generated_by_fkey` — the migration must not hard-assume it; and the change applies via Supabase MCP as item 39 of the canonical run order, per the project's final-writer migration discipline.

## Goals / Non-Goals

**Goals:**
- Repoint `paper_ballot_batches.generated_by` to `admin_sessions(id) ON DELETE RESTRICT` in one atomic, idempotent migration.
- Provable data-safety: pre-check that the column is entirely NULL before altering the constraint (fail loudly otherwise).
- Keep canonical run order and CHANGELOG coherent.

**Non-Goals:**
- Re-enabling RPC writes to `generated_by` (separate decision, needs attribution UX review).
- Touching the already-correct `paper_ballots` actor columns (Wave 6 owns them).
- `admin_principals`, advisory-lock fix, audit-fallback hard-fail (separate backlog items).
- Any application-code change.

## Decisions

1. **`ON DELETE RESTRICT` (not SET NULL / CASCADE).** Matches both precedents (`migration_fix_admin_id_fk.sql`, Wave 6). Attribution, once written, must not silently vanish with a purged session. Alternative considered (SET NULL) preserves purge convenience but loses attribution history — wrong default for an audit-adjacent column.
2. **Dynamic constraint discovery.** Drop the FK by looking up the actual constraint name from `pg_constraint`/`pg_attribute` rather than assuming the `*_fkey` name — idempotent and robust to naming drift. Alternative (hard-coded name) is brittle.
3. **Guarded NULL check as a hard precondition.** `DO` block asserts `NOT EXISTS (SELECT 1 FROM paper_ballot_batches WHERE generated_by IS NOT NULL)` and raises before touching the constraint. If a future state has data, the migration stops instead of silently changing semantics mid-election.
4. **Semantics change NO ACTION → RESTRICT is explicit.** Documented in the spec (session-purge scenario).
5. **Final-writer discipline.** The new migration is the only definition of this constraint going forward; it is appended to the canonical run order in `docs/TECHNICAL_GUIDE.md` as item 39, running after item 38. (`seed.sql` stays last of the *base rebuild* — item 21 — but later migrations run after it; that is the established convention.)
6. **Pre-flight against the live DB before authoring DDL.** Lesson recorded: for schema questions, the live DB (or the final-writer migration) is ground truth — additive historical migration files describe past states, not the present one. The original five-FK premise came from reading Option E part1 without checking Wave 6's final-writer status.

## Risks / Trade-offs

- [RESTRICT blocks purge of an attributed `admin_sessions` row] → Acceptable: column unwritten for now; when writes are re-enabled, attribution retention wins over session cleanup convenience. Session purge housekeeping must tolerate FK-blocked skips.
- [Live DB may already hold unexpected rows in the column] → NULL pre-check raises; rerun safe after investigation. (Verified all-NULL at pre-flight.)
- [Constraint-name drift across environments] → dynamic discovery via pg_constraint.
- [Mid-election application] → NOT to be applied mid-election. Apply only in SETUP phase alongside other maintenance. Recorded as a task gate. (Phase verified SETUP at pre-flight.)

## Migration Plan

1. Apply `supabase/migration_repoint_paper_actor_fks.sql` via Supabase MCP (canonical item 39, after the wipe RPC; SETUP phase only).
2. Verify: `pg_constraint` shows `generated_by` → `admin_sessions` with `ON DELETE RESTRICT`; known-bad input test: set `generated_by` to a member UUID → must FK-violate; set to a real session UUID → succeeds (both inside a rolled-back transaction).
3. Rollback: re-point to `members(id)` via `migration_repoint_paper_actor_fks_rollback.sql` (written but not run; column is NULL so both directions are trivial alter-constraint).
