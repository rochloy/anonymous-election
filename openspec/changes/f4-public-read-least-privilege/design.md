# Design

## Context

See `proposal.md` and `specs/public-election-reads/spec.md` for motivation and behavior. Four unauthenticated Next.js routes currently use the server-side service-role key. The production preflight reported RLS enabled and `anon`/`authenticated` table SELECT denied on `ballots`, `candidates`, and `election_settings`, although three older permissive `PUBLIC` SELECT policies remain. Production is empty SETUP after synthetic UAT; a minimal localhost-only Supabase stack supplies populated pre-close/published tests and isolated fault injection. Empty production smoke tests cannot prove those guards work. The local CLI project lives outside the repo, is unlinked from the hosted project and has automatic seeding disabled. Its **F4 schema-only bootstrap** uses the 45-file canonical list as a source of relative DDL order but deliberately omits the incompatible item-21 `seed.sql` (which references a table created at item 31), inserts the live-required `admin_sessions.scope` migration after item 7, and conditionally guards an obsolete missing-function REVOKE at item 17 in local in-memory replay bytes only. The three older preprinted-ballot patches are superseded by later final writers and are not replayed. None of these local exceptions changes the source SQL or certifies the published 45-file sequence as a valid fresh rebuild. A separate three-ballot synthetic fixture supplies test data after schema replay. Keep Postgres, PostgREST and the API gateway; omit optional services where health checks permit. Never print local keys or use linked/remote reset commands.

The paper-facing `/verify` UI uses the printed paper ballot ID. `submit_paper_vote` also generates a `PB-` receipt returned to the admin, but there is no established delivery of that code to a paper voter; this design does not invent one. The published `/results` route retains a receipt-found lookup for a caller who already possesses either a digital or paper receipt. F4 does not change that policy or add `PB-` support to `/verify`.

## Goals / Non-Goals

**Goals:** Put an independently testable, least-privilege database boundary behind each public read; preserve the four public route contracts except the explicitly corrected unknown-ID-plus-valid-receipt case; make database faults distinguishable from genuine negatives; deploy without disrupting admin/write routes or clearing election data.

**Non-Goals:** Replacing the privileged admin and token-authenticated flows, changing who receives paper receipts, guaranteeing anonymity against privileged database operators, claiming public lookups are rate-limited via Next.js alone, broadening direct table grants, rerunning `schema.sql`, or declaring the project ready for real PII on F4 closure alone.

## Decisions

1. **Four focused read contracts, not raw table grants or a view.** Add one public RPC each for election status, active candidates, vote verification, and published results (including the optional receipt-found flag). Each returns an explicit bounded JSON object/array built from selected columns, never a table row type or raw ballot set. Choose named signatures and document JSON shapes in migration tests. The anon key may call these RPCs directly, so input checks, no-choice output, and pre-publication gating live in SQL, not only in Next.js. A candidates-only RLS view would be defensible but would introduce a second public access pattern for minimal benefit; the four-RPC pattern makes the boundary reviewable in one place.

2. **Dedicated, non-bypassing owner with column-scoped reads.** Provision an `NOLOGIN NOSUPERUSER NOBYPASSRLS` role that does not own source tables; confirm its inherited grants and memberships before use. Grant only `USAGE` on the relevant schema and column-scoped SELECT needed for the four contracts: settings id/phase/dates/nomination options; candidate id/display columns, `is_active`, and `created_at` for ordering; ballot id/receipt/channel/cast date/candidate id for verification and tally. Give it no write privileges or persistent schema `CREATE`. Add RLS policies targeted to that owner: settings row id=1, active candidates, ballot rows including during voting for verification. The phase gate for results is inside the results RPC: the owner's ballot policy must not falsely hide pre-close recorded ballots. Validate the effective owner grants and policy behavior with a seeded pre-close ballot. If the deployed migration actor cannot safely create/own functions as this restricted role, stop and design an equivalent minimum-privilege owner; do not silently leave `postgres` as the function owner.

3. **Lock down SECURITY DEFINER explicitly.** Use trusted fixed `search_path` (prefer `''` with every relation and built-in schema-qualified); prohibit untrusted dynamic SQL; keep verification lookups exact and bounded, never echo an ID/receipt from a stored ballot. Create owner transfer, exact-signature `REVOKE EXECUTE FROM PUBLIC, authenticated`, `GRANT EXECUTE TO anon`, and PostgREST schema reload in one forward-only additive transaction. Check effective `anon`/`authenticated` privileges rather than trusting grant listings; confirm no unintended overload is public. Existing table-level anon/authenticated SELECT remains denied throughout. M2 later removes only the obsolete three `PUBLIC` read policies after route cutover and checks; retain targeted owner policies and RLS.

4. **Preserve semantics; fix ambiguous paired verification.** `/api/verify` accepts receipt-only `VC-<10 hex>` (canonical lowercase suffix), ballot-ID-only including paper IDs, or a paired ID and valid VC receipt. Paired lookup is anchored to the supplied ID; if absent, return `{found:false}` without receipt fallback. A known ID with a mismatched VC receipt returns `receipt_match:false`. No candidate ID, candidate name, stored receipt, or raw ballot object leaves the RPC or route. Both RPC and route cap input sizes before querying. A valid negative returns a normal negative response, while a database error returns a generic non-200 response; do not treat `.single()`-style errors as an absent ballot. Preserve verification during VOTING as well as after closure.

5. **Publication and status are database-side facts.** A results RPC reads phase and returns only `{published:false,phase}` before VOTING_CLOSED; it must not calculate or return totals or receipt existence until after the gate. After publication, aggregate ballot counts by candidate in SQL and return the existing display fields, percentages and total. `totalVotes` counts **all** ballot rows, including votes for candidates now inactive; `results` includes active candidates only, each percentage divided by that all-ballot total and rounded to one decimal. An optional receipt lookup yields only a boolean, with the route echoing a **length-bounded normalized version of the caller's own input** for the existing results page, never a stored receipt. A missing settings row or read failure is an error, not `SETUP`; candidates retain ascending `created_at` order while not exposing `created_at`. The output shape is validated in the route rather than blindly forwarded; database and runtime errors produce only generic category-only diagnostics and generic HTTP errors.

6. **Server-only anon client; no false abuse-control claim.** Use the existing anon key in a new server-only read client; browser pages continue to call Next routes. Direct PostgREST RPC invocation with the public anon key cannot be stopped by a limiter only on Next routes. Scope this change to least-privilege and explicit abuse-risk documentation; inspect existing independent upstream controls, obtain a separate decision before promising/enabling an end-to-end limiter or changing pre-close lookup behavior. Digital receipt suffixes are only 40 bits of randomness, so do not present the RPC as rate-limited merely because the app route is.

## Risks / Trade-offs

- [Restricted owner fails RLS or lacks column privilege] → Verify pre-close positive lookup and published aggregation through real anon-key HTTP on an isolated populated database; stop before deploy if owner transfer, grants, policies or PostgREST return shape fail. Do not use the empty production election as positive proof.
- [A public definer expands access] → Explicit JSON projection; fixed qualified SQL; no unreviewed EXECUTE; inspect ownership/role membership and run direct anon SELECT and RPC negative tests. Deliberately reintroduce a broad grant in an isolated fixture to show the guard fails.
- [Results leak before close or receipts reveal votes] → Gate results and optional receipt flag inside SQL; verify with two distinct candidates and receipts in each phase. Never expose per-ballot `candidate_id` alongside receipt/ID.
- [An operation or DB error looks like a valid negative] → Route-level fault-injection tests and SQL fault cases; return generic non-success; preserve category-only logs.
- [Public existence oracle remains brute-forceable via direct RPC] → Document residual and confirm actual network controls, not an app-only claim. A new end-to-end limiter needs a separately reviewed data/availability design and does not become a prerequisite invented in this F4 spec.
- [Mixed-version rollout breaks public routes] → Add and verify RPCs before switching routes; delay policy cleanup until after live cutover. Keep a known-good Vercel deployment available for rollback, and retain additive RPCs during app rollback.

## Migration Plan

1. **Preflight:** on a clean feature branch, inventory live function names/owners/overloads, owner role membership and effective grants, PostgREST exposed schemas, three source-table privileges/policies, and presence of all required columns. No production data mutation. Review tests for deliberately broken input and local isolation. Reproduce the **schema-only local bootstrap** described above and a minimal synthetic fixture only in the localhost stack; stop on a replay error or privilege/extension parity difference and rebuild the local database before retrying. Check actual anon-key HTTP against the local gateway, not only SQL role simulation. Monitor Docker footprint against the user's 70 GB practical disk budget: stop if effective free space approaches 25 GB, and never perform broad Docker prune or remove unrelated volumes.
2. **M1 / additive:** in a new canonical terminal migration create restricted owner + scoped grants/policies + four RPCs, set owner and exact ACLs, reload PostgREST. This creates no ballot data and leaves old app routes functional. Verify via live anon-key PostgREST: exact RPC grants, no direct table SELECT, status and candidates in current SETUP, invalid ballot ID, unpublished results, and generic failures. Exercise successful verification during VOTING and published tally/receipt behavior on the populated local stack.
3. **App cutover:** test route contracts/error injections in-process, build/lint, obtain branch merge/deploy approval, deploy via Vercel CLI. Confirm the four routes use only the restricted anon client (including a known-bad static route import check), public outputs match, and admin/token-authenticated behavior is unaffected. If a route fails, roll back the app deployment without revoking the already-added RPCs.
4. **M2 / policy cleanup:** only after live route cutover checks and separate migration approval, drop the old broad `PUBLIC` SELECT policies in a second forward migration. Reconfirm RLS, denied anon/authenticated table reads, owner-targeted policies, all four RPC contracts, and public smoke responses. If M2 fails, leave F4 open and diagnose before retry; do not turn on direct table SELECT to hide a broken RPC.
5. **Completion gate:** document observed role, ACL, seeded-phase, route and production smoke results; reconcile SECURITY.md and other docs only when all evidence is in place. Do not mark F4 closed or imply real-PII clearance merely because migration SQL was applied.
